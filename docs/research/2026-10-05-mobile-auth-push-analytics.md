# Mobile auth, mobile push, and anonymous analytics — research

Date: 2026-10-05. Scope: `docs/backlog.md` items "Mobile auth", "Mobile push", "Anonymous player analytics".

## 1. Current web auth

Web auth is a hand-rolled JWT system on Web Crypto, no external auth library.

- **Email/password**: `POST /auth/register`, `POST /auth/login` — PBKDF2 (100k iterations, SHA-256, random 16-byte salt) via `hashPassword`/`verifyPassword` (`apps/backend/src/utils/auth.ts:70-99`).
- **JWT**: HS256, signed/verified with `crypto.subtle` HMAC, no library (`apps/backend/src/utils/auth.ts:37-68`). Payload is `{ sub: userId, exp }` only — no `iat`, no `aud`/`iss`. Lifetime `JWT_EXPIRES_IN = 30 days` (`apps/backend/src/routes/auth.ts:30`). Secret is `env.JWT_SECRET`.
- **Storage**: frontend stores the raw token in `localStorage` under `harfhane:token` (`apps/frontend/src/context/AuthContext.tsx:24,60`), not an httpOnly cookie. XSS would leak it.
- **Refresh**: `POST /auth/refresh` (requires valid token) reissues a token; frontend calls it when `exp` is within 7 days (`REFRESH_THRESHOLD_SECONDS`, `AuthContext.tsx:5,76-88,101-121`), checked on load, every 10 minutes, and on tab-visible.
- **Google OAuth (web, authorization-code flow)**: `GET /auth/google` redirects to Google with `redirect_uri=https://api.harfhane.app/api/auth/google/callback` (`auth.ts:34,138-147`); `GET /auth/google/callback` exchanges the code server-side (`exchangeGoogleCode`, `auth.ts:49-69`), calls the legacy `userinfo` v2 endpoint (`GOOGLE_USERINFO_URL`, `auth.ts:33,71-81` — Google's newer guidance is to decode the ID token instead of a second userinfo call, see §2), then `upsertGoogleUser` and redirects to `APP_URL?token=...` (`auth.ts:149-171`). The app then picks the token up from the query string (`AuthContext.tsx:52-74`).
- **Tables** (`apps/backend/db/migrations/0001_baseline.sql:50-60`): `users(id, email, username, password_hash, google_id, …)`, unique partial index on `google_id` where not null. Google-only accounts get `password_hash = 'GOOGLE_AUTH'` as a sentinel (`user-repository.ts:53`), and `forgot-password` treats that sentinel as "no reset" (`auth.ts:192`).
- `requireAuth` middleware (`apps/backend/src/middleware/auth-middleware.ts`) reads `Authorization: Bearer`, verifies, sets `userId` in context — this is the hook mobile verification should also populate.

## 2. Native Google Sign-In on Expo/Android

- **Library choice**: `@react-native-google-signin/google-signin` is the standard native-module package; it wraps Android's **Credential Manager** (Google's current API, replacing the deprecated Sign-In SDK and One Tap) and iOS `GoogleSignIn`. `expo-auth-session` is a pure-JS browser-based OAuth flow (AppAuth) and works in Expo Go, but gives a worse native UX on Android and Google is pushing apps toward Credential Manager. Credential Manager support in `@react-native-google-signin` is reported as a paid add-on in some distributions; `react-native-nitro-google-signin` is cited as a free alternative with built-in Credential Manager support (WebSearch, 2026-10, no official Google source found for the paywall claim — unverified, confirm before committing to a library).
- **Dev build requirement**: native Google Sign-In needs custom native code, so it cannot run in Expo Go. Requires a config plugin in `app.json`/`app.config`, `npx expo prebuild`, and an EAS development or production build (Expo docs, `docs.expo.dev/guides/google-authentication/`, 2026-10).
- **Client IDs needed**: a **Web** OAuth client (already exists — `env.GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` used by the web flow, `auth.ts:54-55`) plus a separate **Android** OAuth client ID (keyed to the app's package name + SHA-1 signing fingerprint) registered in the same Google Cloud project. The ID token the mobile SDK returns is signed for the Android client, but its `aud` claim must be checked against the Android client ID (or both, if accepting from either surface).
- **Verifying the ID token on Workers**: Workers runs on `workerd`, not Node — so Google's own `google-auth-library` (Node-only) cannot be used. The standard approach (Kinde/Cloudflare community docs, 2026-10) is: fetch Google's JWKS at `https://www.googleapis.com/oauth2/v3/certs`, select the key by `kid` from the token header, and verify with the `jose` library's `createRemoteJWKSet` + `jwtVerify` (works unmodified on `workerd`, no Node polyfills needed) or with raw `crypto.subtle.importKey`/`verify` if avoiding a dependency. Verify `iss` (`https://accounts.google.com`), `aud` (the Android client ID), and `exp`; cache the JWKS in Workers KV or just rely on `jose`'s in-memory cache per isolate to avoid refetching every request.
- **Proposed endpoint**: `POST /api/auth/google/mobile` taking `{ idToken }`. Verify as above, extract `sub` (Google's user id) and `email`, then reuse `upsertGoogleUser` (`user-repository.ts:60-72`) and `signJwt` exactly as the web callback does (`auth.ts:162-166`) — this reuses the existing `users` table and JWT shape with zero schema change, and the mobile client ends up with the same bearer token contract the web client already uses.
- **Is sign-in required for MVP?** No — the current write path already supports anonymous use: `game_results` only gets written by `requireAuth`-gated `POST /results` (`apps/backend/src/routes/results.ts:17`), and nothing else forces login. An Android MVP can ship as anonymous-play-first, offering Google Sign-In only to unlock sync/leaderboard/streak-freeze, same as the backlog's "Anonymous player analytics" item implies the web app already does.

## 3. Push: current state and mobile extension

- **Web push today**: VAPID-signed Web Push, hand-rolled (`apps/backend/src/utils/web-push.ts`) — ECDH/HKDF/AES-128-GCM payload encryption and ES256 VAPID JWT, all via `crypto.subtle`, no library. Routes: `POST /push/subscribe`, `DELETE /push/unsubscribe`, `GET /push/vapid-public-key` (`apps/backend/src/routes/push.ts`), all but the key endpoint behind `requireAuth`. Table: `push_subscriptions(id, user_id, endpoint, p256dh, auth)` with a unique `endpoint` (`0001_baseline.sql:137-145`, upsert in `push-repository.ts:9-25`).
- **Cron**: `wrangler.toml:25` → `crons = ["0 17 * * *"]` (17:00 UTC daily). `scheduled()` in `apps/backend/src/index.ts:94-119` finds subscriptions for users who have **not** played today (`getSubscriptionsForUsersWithoutTodayPlay`, anti-join against `game_results` by date, `push-repository.ts:38-55`), builds a hint from the daily word's meaning/category, and fires push + a parallel reminder email via `Promise.allSettled`.
- **Expo push vs. direct FCM**: Expo's push service (`ExponentPushToken[...]`) is a hosted relay in front of FCM/APNs — handles auth, batching, retries, and delivery receipts, and is the standard choice unless sending >~several hundred thousand/day or needing FCM-native analytics (Expo docs + comparison articles, 2026-10). Given Harfhane's scale, Expo's push service is the pragmatic choice; direct FCM v1 (OAuth2 service-account JSON, legacy server-key API fully retired) is the fallback if Expo's service becomes a bottleneck.
- **Design**: add an `expo_push_tokens(user_id, token, …)` table (or extend `push_subscriptions` with a `platform` discriminant and nullable web-only columns) and mirror `/push/subscribe`/`/push/unsubscribe` for Expo tokens. In `scheduled()`, after resolving the same "didn't play today" set, send Expo pushes via a batched `POST https://exp.host/--/api/v2/push/send` call (same job, same anti-join query, two sends instead of one) rather than per-token HTTP requests like the current web-push loop. Expo returns per-token receipts (success/`DeviceNotRegistered`/etc.) in a second receipt-check call — on `DeviceNotRegistered`, delete the stored token, mirroring how expired web-push `endpoint`s should eventually be pruned (not currently done — the backlog doesn't mention it, flagging as a related gap).

## 4. Anonymous analytics vs. privacy

- Only `requireAuth`-gated `POST /results` writes `game_results` — anonymous play leaves zero server-side trace today. No `analytics`/`Analytics` references exist anywhere in `apps/frontend/src` or `apps/backend/src` (grep, empty).
- **Cloudflare Web Analytics**: injects a lightweight JS beacon, explicitly "does not set any cookies, use localStorage, or store any identifiers on the visitor's device" and computes aggregate visit counts with no visitor ID or fingerprint (ctrl.blog technical review + Cloudflare's own privacy-first claims, 2026-10). This is the simplest fit for "how many people loaded the page" but only measures page views, not game outcomes (won/lost, word length, streak).
- **Cookie-free aggregate game-play counter**: to count anonymous plays specifically (not just page loads), add a counter endpoint that increments a daily aggregate — e.g. `POST /api/stats/play` with no user identifier, writing to a `daily_play_counts(date, word_length, mode, count)` style table via `UPDATE ... SET count = count + 1` (or a D1/KV counter). No IP, no cookie, no device id stored — just an integer bump keyed by date+length+mode, which answers "how much is the game actually played" without identifying anyone. This complements rather than replaces Cloudflare Web Analytics.
- **Privacy policy status**: there is **no live privacy policy page** in the frontend today. `apps/frontend/src/components/SettingsModal.tsx:243` renders a plain, non-clickable "Gizlilik" label (`<span>`, not `<a>`) — a placeholder with no destination. `docs/backlog.md`'s "Anonymous player analytics" item says "the privacy policy must stay accurate," but there is nothing to keep accurate yet; writing or linking a real KVKK-compliant privacy text is a prerequisite, not an update.
- **KVKK**: Turkey's KVKK (Law No. 6698) governs processing of personal data; a cookie-free, non-identifying aggregate counter and Cloudflare's cookieless analytics plausibly fall outside "personal data" processing (no PII, no identifiers), but this is a legal judgment call the owner should confirm — flagged as unverified below, no authoritative KVKK guidance on cookieless aggregate counters was found in this research pass.
